## 二、官方文档依据（mimo.mi.com 图片理解文档）

- **模型能力**：`mimo-v2.6-flash` 为原生全模态模型，输入模态=文本/图像/视频/音频，同时支持工具调用、结构化输出、上下文缓存；上下文 1M tokens。
- **格式**：JPEG、PNG、GIF、WebP、BMP。
- **大小**：单张 ≤ 50 MB（base64 字符串大小计）。
- **张数**：无硬性上限，仅受上下文总 token 限制（1M 上下文下几十张也放得下）。
- **计费**：图片按 token 计（1024×1024 约 1024 tokens；手机截图 780×1688 实测 1272 tokens）；重复图片可命中**上下文缓存**（cached_tokens）减费。

## 四、"单次打包存储"方案设计（推荐落地形态）

### 存储（你说的"单次打包"成立）
- `AiMessage` 表加一列 `ImageMime` + `ImageData`（byte[]），图片随消息**存一次**，不做图床/相册/对象存储。
- SQLite 存几百 KB 的图毫无压力；10 人自用规模无需归档策略，可选"90 天后清图只留文字"兜底。
- 权限天然安全：AiMessage 已有 UserId 隔离 + `perm:ai.use` 围栏。

### 发送（两个策略，推荐 A）
- **策略 A · 真单次（推荐）**：图片只随「当轮」请求打包发送；进入历史后只保留缩略图给用户看。省 token、隐私好、语义就是"看一眼图办事"。
  - 代价：追问"图里那个字是什么"时 AI 不再认图——需要时用户重新发一次即可。
- 策略 B · 随历史重发：图片跟着最近 20 条历史每次重打包。可连续追问，靠上下文缓存降费（约 1.3k token/图/轮）。

### 前端
- 输入条加 📷 按钮（手机调相机 `capture` 或相册），选图后 canvas 压缩（限宽 1600px、JPEG q0.8，手机原图 3-5MB → 约 200-400KB）+ 缩略图预览 + 可删除。
- 限 1 张/条（先简单；多图 API 本身支持，以后放开）。

### 后端改动量（约半天）
1. `AiChatMessage.Content`：string → 内容块数组序列化（或加 `ImageUrl` 字段，打包时拼 `[image_url, text]`）——约 10 行。
2. `AiMessage` 迁移加 2 列 + Send 流程接收图片（base64 校验、MIME 白名单、大小上限 5MB）。
3. Ai/Index.cshtml + JS：上传控件、压缩、预览。
4. 日配额 60 条不变；图片 token 开销约 1.3k/张，对 1M 上下文与 flash 定价可忽略。

## 五、风险与边界

| 风险 | 评估 |
|---|---|
| 图片撑大请求 | base64 上限 50MB 远用不到；客户端压缩 + 服务端 5MB 硬顶双保险 |
| 库体积膨胀 | 限 1 张/条 + 压缩后每条 <500KB；可选 90 天清图 |
| 模型看错图 | flash 视觉能力中上（OCR/计数可用，复杂推理一般）；生活管家场景（拍课表/票据/截图问问题）够用 |
| 响应变慢 | 带图 5-8 秒；现有"思考中…"状态已覆盖 |
| 日期推理错 | 系统提示带当前日期（已有），实测确认必须 |
| 密钥安全 | 不变（key 仍只在 appsettings.Local.json / 环境变量） |
